# Findings: technical rules and rationale

This reference records measured observations and their rationale. Read applicable rows at M0, M2 and M3. Workflow authorization belongs to STATUS, semantics to SPEC, and mechanical thresholds to the runtime. Report a discrepancy to the orchestrator; workers retain their source ownership. Historical efficiencies below are observations, not alternate passing thresholds.

## Performance judgement

| finding | rule | where |
|---|---|---|
| The datasheet tensor-core peak is not an achievable GEMM roof: cuBLAS lands at 70-85% of it by shape, and `torch.compile(mode="max-autotune")` can tie cuBLAS with the epilogue fused | The achievable compute roof is **measured cuBLAS on the phase's GEMMs** (`gemm_shapes` in `_speed_of_light.py`, timed by `bench.matmul_ms`), as the memory roof is a measured same-size copy; the compile baseline for tensor-core ops is `max-autotune-no-cudagraphs`. Matching compile is the realistic speed of light for a GEMM fusion; do not tune towards the datasheet number | `_run_dev.py`, `speed-of-light.md`, `compute-patterns.md` (`gemm_tensorcore`) |
| A phase near the launch-latency floor can be much faster than eager while still reporting low `sol_eff` against a copy roof | The runtime applies the 10 us latency floor, 5% baseline parity band and its absolute latency-parity allowance; use its verdict without a reference-specific override | `report.py` (`LATENCY_FLOOR_MS`, parity band), `speed-of-light.md` |
| Missing byte terms or incorrect GEMM counts can make a reported roofline physically impossible | `sol_eff = achievable_roof / kernel_ms`; a ratio above one warrants checking the measured roof, counts and timing, and is not a datasheet violation by definition. Compare `kernel_ms` with datasheet `sol_ms` separately. Missing GEMMs lower the estimated roof and this ratio | `report.py` (`below_datasheet_roof`), verify skill "Roofline plausibility" |
| One program per row reaches the copy roof up to `D = 32768`; a split adds a launch and a read even when there are fewer rows than SMs | Use the measured one-program-per-row geometry as the default through `D = 32768`; test alternate geometry only with evidence for the actual workload | `compute-patterns.md` "Row width rule" |
| TileLang GEMM + epilogue reaches 0.8x of its Triton twin on the up/down-projection forwards (`T.dynamic` strides halve the mainloop, fragment stores to global cost 6x, the Triton-winning tile loses); on A800 the Triton mainloop can trail cuBLAS by more than the epilogue traffic on wide outputs | Select a supported explicit user backend first; otherwise applicable nvmath, otherwise Triton. Under Triton, compare `torch.matmul` plus the required epilogue when the mainloop gap warrants it; the measured TileLang comparison does not override user choice | `compute-patterns.md` "Backend note", "Mainloop note" |
| An isolated kernel speedup need not shorten the complete training step | Time the model-context forward and backward separately (the kernel may sit off the critical path, or the backward may have gained what the optimizer lost); a flat step is a diagnosis to write, not a verdict | integrate skill "flat step time" |
| The four FA2 references (Triton and TileLang, causal and dense GQA) reach 0.85-0.94x of torch's FA2 kernel forward and 0.7-1.2x backward, 8-22x over eager, 53-63% of the datasheet peak; the remaining gap is FA2's hand-scheduled softmax/GEMM overlap | These reference ratios (including 0.5 efficiency and 0.9x SDPA) are observations. The runtime selects the eager/compiled baseline and applies its normal thresholds; SDPA is an additional diagnostic, and attended-area FLOPs define the operation count | `compute-patterns.md` (`flash_attention_2`), `reference/*/attention/*/SNIPPET.md` |
| TileLang FA2 lowering requires `GemmWarpPolicy.FullRow` when an accumulator feeds another GEMM, `num_stages=1` for deterministic tail tiles, no `if` around shared reads inside `T.Pipelined`, explicit handling of uninitialised 1-D `T.copy` tails, one staging tile per store, and power-of-two `D` for fragment reductions | Follow the TileLang attention page's lowering rules; check determinism with `torch.equal` over repeated backward runs with poisoned memory between them | `tilelang/attention/fa2_causal/SNIPPET.md`, `tilelang/README.md` |
| Shape-specialised TileLang JIT costs multiply across workloads and phases, especially for attention backward | Use the ordered backend rule above. Budget TileLang JIT time; scoped M2/M4 commands require explicit diagnostic JSON and Markdown paths | `compute-patterns.md` (backend note), scaffold step 2, `tilelang/README.md` |
| cuBLAS on per-head `(B*H*S, S, d)` attention GEMMs is slow at skinny `K = d`, so using it as the roof can give `sol_eff > 1` | `flash_attention_2` uses `ROOF_METHOD="attention"` with independent native geometry and useful pair count; the runtime measures phase-matched dense Flash throughput, scales by attended density and retains the copy floor. Verify applicable SDPA on the actual contract as a separate baseline | scaffold step 6, `_speed_of_light.py` docstring, `compute-patterns.md` |
| Scanning a tile mask inside the device loop adds gather/reduce/branch work for every key tile; host-built block lists avoid this, and heavy-first program order reduces the tail wave for heterogeneous heads | Block-sparse attention: block lists on the host, an indirect unmasked loop plus a short masked loop on the device, `perm`-sorted program order when heads differ, `-inf` guard for fully-denied rows | `compute-patterns.md` "Block-sparse attention", `examples/sliding_tile_attention/golden/` |
| `--method auto` can fall back to `events` after a CUPTI failure, and event timing can miss kernels or include host overhead | An `events` record is never the record: re-run with `--method profiler`; a rejected tune restores the checkpointed source and finalized evidence while retaining the hypothesis log and dispatched run counters | implement SKILL §bench, verify SKILL §2, orchestrator M3/M4 |
| On A800 with TileLang 0.1.13/0.1.14, execution backends change compile/launch overhead, not device code (`nvrtc`: 4.4 s compile and 21 us launch; `tvm_ffi`: 5.7 s and 10 us); interleaved timing is needed to distinguish tile changes from clock drift | Do not look for a TileLang flag: its performance is codegen, and the only lever is compile count. Declare grid-only extents `T.dynamic` (`M`, `B`, `H`: measured free) and loop-bound extents `T.const` (`N`, `K`, `S`, `D`: dynamic `S` costs 13% device time); take `nvrtc` when compiles dominate and the kernels are long, `tvm_ffi` for many short launches; never name a tensor argument `res`. Any tile or flag comparison is round-robin against a fixed reference, never sequential | `reference/tilelang/README.md` (flag study), `tilelang-wiki/references/targets.md`, the three TileLang reference kernels |
| nvmath-python's cuBLASLt `GELU_AUX_BIAS` epilogue, planned once, reaches 1.04 ms on the 8192x8192x2048 MLP (1.16x eager, 1.15x compile, 2.5% above bare cuBLAS); its heuristic can also outperform `torch.matmul` on the down-projection (315 vs 369 us) | Respect a supported explicit backend choice first; otherwise select `kernel_backend: nvmath` when `import nvmath` works and the epilogue is bias / ReLU / tanh-GELU (+ aux); second `torch.matmul` + one pointwise epilogue kernel; a fused Triton GEMM only for what cuBLASLt cannot express. Carry two facts into the SPEC: cuBLASLt's GELU is the tanh form (name the form the user's code calls; erf differs by 2e-3), and there is no post-activation residual (the next norm adds it). Plan once per shape, `execute()` costs 130-175 us of host time, so below ~200 us of device time in eager the `torch.matmul` path wins | `reference/nvmath/epilogue/gemm/SNIPPET.md`, `compute-patterns.md` (mainloop note), `examples/fused_gemm_epilogue/golden/GOLDEN.md` |

## Numerics

| finding | rule | where |
|---|---|---|
| Cancellation in `gelu(z) + r` near zero makes the mainloop's rounding point part of the output contract | Numerics can decide the mainloop: reproduce eager rounding and probe candidates on model-scale inputs; cancellation alone cannot choose between fp32 accumulation and rounded cuBLAS intermediates. Record the observed contract and aux form in SPEC | scaffold skill "numerics-first mainloop", `triton/epilogue/gemm/SNIPPET.md` |
| A numerics decision made on model-scale inputs does not transfer to unscaled `randn`: GEMM intermediates grow as `sqrt(K)` rather than staying near the model's init scale | `make_inputs` reproduces the model's scales (GEMM weights at init std, norm weights ~1) *before* any numerics decision, and the decision is made by a probe on those inputs at step 8; the gate names the aux form | scaffold steps 5 and 8, `_run_dev.py` `make_inputs` |
| Fused fp32 `Z`, bias-inclusive cuBLAS `addmm`, and cuBLAS `matmul` followed by fp32 bias have different rounding points; the usual rule of thumb cannot choose for every input | The probe is run for every candidate rounding point of the mainloop output and the zero-failure row is the design; the rule of thumb names the usual winners, not the only ones | scaffold step 8 (probe code) |
| Eager rounds mixed-dtype arithmetic such as `1 + scale` in bf16 before an upcast, which matters near `scale = -1` | The eager reference's own rounding points are part of the contract; list them from `_eager.py` and reproduce them in the kernel | implement skill "Compute dtype" |
| A producing `Linear` under autocast can emit bf16 conditioning tensors even when the task describes fp32 | Intake probes dtypes, shapes and strides by running one step of the smoke command with the region wrapped; SPEC dtypes come from the print, not the prose | scaffold step 1, orchestrator "SPEC correction after M5" |
| Optional representative workloads may cover a different numerics regime from the required user workloads | The M2 tick and the M3 verdict use the **required** rows; an optional row's numeric failure is a note in the SPEC and REPORT, not a gate | orchestrator M2, `report.py` |
| bf16 reassociation can change integrated model loss without violating the kernel's numerical contract | Model loss and grads vs the original code are compared at SPEC tolerance, not bitwise; the bitwise check is eager-backend-vs-before | integrate skill §3 |
| A mismatch between a `torch.library` fake and the real auxiliary shape can pass eager checks but fail compiled backward; stale compilation caches can hide a fix | The `--verify` run carries a `torch.compile(fullgraph=True)` probe on the first user row, with inductor caches off and donated buffers off for the dev process | `_run_dev.py` `_compile_probe`, `bench.configure_compile_for_dev` |
| Large verification graphs, outputs and gradients can consume ~15x the input memory; an eager fp32 norm can hold ~10 temporaries of 8 GiB at the 2^31-element boundary | Comparison is chunked; verification tensors are freed before the bench; an optional row that still runs out of memory is recorded as skipped, required allocation failures/preflight skips as incomplete evidence, retaining any known numerical failure | `verify.py`, `_run_dev.py` |
| Tuning can require a different saved-for-backward contract, such as a bf16 weight copy to avoid a repeated cast | The orchestrator amends SPEC/roofline/eager inline before the tune dispatch, re-runs the eager sanity and logs the amendment; the tune implementer receives the amended contract | orchestrator M4 |
| A verifier's proposed bottleneck may be false; model-generated RoPE tables also contain structure that arbitrary random tables do not preserve | The `Diagnosis:` line is the first hypothesis, not an instruction; `make_inputs` builds tables with the model's own table function (duplicated halves in `[-1, 1]`), since a `randn` table cannot tell a kernel that exploits the duplication from one that does not | implement §3, scaffold step 8 |
| A smoke run that resamples random targets every step can amplify a 1-ulp operator difference over 50 steps | Past ~1e-2, isolate with one step on identical weights and data, eager vs kernel per call, and report that number next to the 50-step one; the eager-flag row stays the bitwise check | integrate §3 |
| adaLN's modulation `chunk()` views can use row stride `6D` at blocks and `2D` at the final layer; inspecting only the first call misses a layout | The intake probe prints every call of one step, each distinct layout is a `user_` row, the example strides the tensors the model strides | scaffold step 1, workloads.md adaLN set |
| A per-element fp32 sigmoid is ~30% of the copy time in MUFU issue at `D = 1152` (x1.8 over a `BLOCK_D = 2048` tile); the copy roof and FMA FLOP roof do not capture that SFU cost | Named as structural in speed-of-light.md ("SFU work under the copy roof", with the arithmetic); a fast sigmoid and chunking buy 5-10 points, then the orchestrator accepts best-so-far after one round instead of two | speed-of-light.md, implement §3 table, orchestrator M4 |
| Re-verifying an unchanged kernel after a reverted tune round adds work without new evidence | A tune round that reverts to the previous code keeps the previous report as its record and skips the M3 re-run | orchestrator M4 |
| Shared-device interference moves baselines and can flip a gate inside the noise band | Check device interference and preserve two prescribed diagnostic repeats for a near-gate row. A gate that flips is unresolved (`incomplete`), with every sample retained; two integration smoke repeats more than 10% apart get a third | verify skill §4, integrate skill §3 |

## Shapes and indexing

| finding | rule | where |
|---|---|---|
| An oversized `edge_huge` row that cannot run never exercises the int32 overflow it is meant to catch | int32 element offsets overflow at 2^31 elements = 4 GiB bf16; `edge_huge` is the **smallest** crossing (`[262145, 8192]`, a `131073 x 16384` GEMM plane with `K = 256`, a `1 x 8 x 16512^2` score plane); `validate_spec` rejects rows above 13 GiB of inputs and a big edge row that crosses nothing | `workloads.md`, `spec.py` `_size_errors`, `compute-patterns.md` "Indexing rule" |
| The same 2^31 is an ordinary size, not an edge: attention scores at 56 heads x 6200 tokens, `(M, N)` planes of 65k-token GEMMs, long-context `(B, S, D)` activations | `row = tl.program_id(0).to(tl.int64)` before any stride multiply, in every launcher; the verifier's index-safety row checks it | implement skill "Offsets", verify skill |
| Promoting the FA2 row program id to int64 wholesale also promotes loop bounds and in-loop addresses; the reference comparison measured an 11% cost (3.11 -> 3.47 ms at 8192 tokens) | int64 for the `(b, h)` base and the program's own tile (outside the loop), int32 for the offsets inside the K,V loop, with a host assert that one `(b, h)` plane spans `< 2^31` elements; the lint's `int64` rule accepts the `.to(tl.int64)` on the same id | `triton/attention/fa2_causal/SNIPPET.md` "int64, but not in the loop" |
| Inferring row inputs solely from matching sizes can empty a GEMM weight when `N == M` | SPEC `row_inputs` names the inputs that carry the token dim | `spec.py`, `_run_dev.py` |
| Making q/k slices of a fused `qkv` buffer contiguous adds a full memory pass | Preserve the observed strided inputs and add a `user_strided` row. The generic row helper supports collapsible leading dimensions; other layouts need an explicit supported addressing scheme or a bounded limitation | `workloads.md`, `interface.py` checks |

## Workflow and reporting

| finding | rule | where |
|---|---|---|
| Profiler and event timings answer different questions, so their verdicts are not interchangeable | M2/M5 correctness evidence uses side files; M3 owns the complete profiler `report.json` and finalizes the verifier decision. M4 timings and events diagnostics use unique side files | verify skill, orchestrator M2 |
| `N_OUTPUTS`, saved tensor accounting, autotune removal, and frozen config limits need precise definitions at their owning stage | Each is now defined in its owning contract, stage or evidence protocol; when a rule looks like it forbids something harmless, the intent is the narrower reading (`@triton.autotune` decorators, not the word) | scaffold step 4, implement `_register.py` and freeze sections |
| Asynchronous subagent dispatch can let an orchestrator advance before implementation completes | Dispatch implementer then verifier sequentially and await each completion using the available harness mechanism. Without workers, record explicit serial role changes and same-context verification | orchestrator dispatch, `kda/agents/README.md` |
| Concurrent writers to the same kernel package can invalidate the implementation and its measurement record | Use one active writer per kernel package; scratch scripts live under `<op_dir>/_scratch/` | orchestrator dispatch, implement skill |
| Report fields and gate status have stage-specific meanings | The table cells and STATUS lines are spelled out where they are filled in, not only in the mermaid | orchestrator, integrate skills |
